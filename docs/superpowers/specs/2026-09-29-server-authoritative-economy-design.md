# 경제 서버 권위 설계 (치트 방지)

작성: 2026-09-29 · 범위 결정: "경제만 서버가 관리" (전투 자체는 클라이언트 유지)

## 왜

지금은 `PATCH /characters/me/progress`가 레벨·경험치·골드·능력치를 **클라이언트가 보낸 값 그대로** 저장한다
(절대 상한만 검사: 레벨 999, 골드 약 10억 등). 또한
- 상점 구매는 골드를 검사하지 않고, 판매는 골드를 지급하지 않는다(골드는 클라이언트 전용).
- `POST /me/inventory/loot`는 클라이언트가 말한 `item_template_id`를 그대로 지급한다(보스 전용 장비도 가능).
- 퀘스트 보상은 서버가 값만 알려주고 적용은 클라이언트가 한다.
- `POST /me/quests/progress`는 킬을 보고만 하면 퀘스트가 진행된다.

개발자 도구 한 줄로 만렙·10억 골드·최고급 장비를 만들 수 있다. 랭킹 등 경쟁 요소를 넣기 전에 막아야 한다.

## 하지 않는 것 (잔여 위험)

몬스터 인스턴스, 데미지, 이동은 계속 클라이언트가 계산한다(서버는 몬스터가 실제로 존재/사망했는지 모른다).
따라서 **API를 직접 호출하는 스크립트가 킬을 가장해 파밍하는 것**은 막지 못한다. 대신 그 이득을 제한한다:
- 킬 보고는 토큰 버킷으로 속도를 제한한다(초당 1.5킬, 순간 최대 25킬).
- 보고된 몬스터 레벨은 그 종류가 실제로 가질 수 있는 최대 레벨 이하여야 한다(`economyRules.ts`).
- 보스는 서버의 리스폰 쿨다운(`record_boss_kill`)을 통과해야 보상이 나온다.

전투 전체를 서버가 관리하는 안(C)은 게임 구조를 크게 바꿔야 해서 보류.

## 원칙

서버가 **골드, 경험치/레벨, 스탯 포인트/스킬 포인트, 파생 능력치(공격력/최대 HP·MP/방어력), 아이템 지급**의 유일한 원본이다.
클라이언트는 화면 반응성을 위해 지금처럼 **로컬에서 먼저 예측**해 보여주되, 서버 응답의 `progress` 스냅샷으로
**경제 필드를 덮어쓴다**. 현재 HP/MP는 클라이언트 값을 신뢰한다(서버가 최대치로만 제한).

## 서버

| 기능 | 라우트 / RPC |
|---|---|
| 킬 보고 | `POST /me/kills` → `apply_kills` (속도 제한, 경험치/골드 계산, 레벨업) + 퀘스트 진행 + 보스 쿨다운 + 드랍 굴리기 |
| 드랍 | 서버가 `drops.ts`의 표로 굴려 `pending_drops`(5분 유효)에 발급 → `POST /me/inventory/loot {drop_id}` → `redeem_drop` 후 지급 |
| 상점 | 구매: `spend_gold` 후 지급(실패 시 환불). 판매: 감소 후 `grant_progress`로 골드 지급 |
| 퀘스트 보상 | `claim_quest_reward`가 경험치/골드를 직접 적용 |
| 스탯 배분 | `POST /me/stats/allocate` → `allocate_stat` |
| 진행 저장 | `PATCH /me/progress`는 `current_hp`/`current_mp`만 받음(최대치로 제한) |

- 규칙(경험치 = 레벨×20, 골드 = 레벨×(4~11), 필요 경험치 = 레벨×100, 레벨업 +20 HP/+2 공격/+3 스탯/+1 스킬 포인트 …)은
  `supabase/functions/api/economyRules.ts`와 SQL에 있고, 클라이언트(`combatStore`)와 값이 같아야 한다.
  `src/stores/serverEconomy.test.ts`가 클라이언트 계산과 서버 규칙이 어긋나면 실패하도록 지킨다.
- 모든 변경은 `characters.progress_rev`를 올린다. 클라이언트는 더 낮은 `progress_rev`의 응답을 무시한다(순서 뒤바뀜 방지).

## 클라이언트

- `killReporter.ts`: 킬을 모아(100ms) 한 번에 보고, 한 번에 하나만 전송. 대기 중인 킬이 없을 때만 스냅샷을 채택해
  경험치 바가 뒤로 튀지 않게 한다. 응답의 드랍을 월드에 생성하고 퀘스트/보스 상태를 갱신한다.
- 광역 스킬로 여러 마리가 죽어도 전부 보고한다(이전에는 대표 1마리만 퀘스트/드랍 처리).
- 상점/퀘스트 보상/스탯 배분은 로컬 예측을 유지하고 응답 스냅샷으로 보정한다.
- 골드가 서버와 어긋나 서버가 거절하면(`insufficient_gold`) 프로필을 다시 받아 맞춘다.

## 배포 순서

1. `supabase db push` (마이그레이션 `20260929010000_server_authoritative_economy.sql`)
2. `supabase functions deploy api`
3. 클라이언트 배포(PR 머지)

1~2와 3 사이에는 잠깐 구버전 클라이언트가 새 서버와 섞인다: 구버전의 진행 저장은 무시되고
구버전의 아이템 줍기(`item_template_id`)는 거절된다. 새로고침하면 해결된다.
